# v2 联调待确认项

## 端点 error 的关联范围

现有 error 只有可空的 refDeliveryId，没有 fromIncarnation/toIncarnation，也没有原投递的 payloadHash。relay 能验证 error 来自当前 connectionId，并将它送到同一配对当前的另一角色。仅凭这几个字段，云端和接收方无法确认迟到 error 是否属于对端重装前的投递。该帧只作错误信号，端点依据自己当前版本的 outbox、观察到的 peer incarnation 和本地记录决定退避或隔离。receipt 仍须匹配完整四元组。

建议下一版明确 error 的目标绑定与语义，例如在协议共审后加入原 deliver 的 incarnation 与 hash，明确 refDeliveryId=null 时的适用范围。当前共享 schema、样例和错误码保持原样。

## 端点持久化指标

现有云端接口没有端点上报指标的帧。云端提供连接、心跳、队列、错误和关闭聚合值。receipt 的持久化耗时、业务 ack 延迟、重复投递、端点哈希冲突和磁盘容量由各端本地采集。若需要统一看板，建议独立确认采集方案与匿名聚合口径。

## 关闭码和短时竞态

设计定义了 4401 撤销、4409 替换和 1013 过载。当前实现给无有效 Pong 的连接发可重试的 1011，给 hello 无效或超时、WS 消息 10 秒组装超时发 1008，给 WS 总长超限发 1009。建议三端联调时确认这些关闭码的客户端提示与是否自动重试。

presence 描述云端观察到的绑定状态。socket 写入开始后，字节可能仍在网络中，替换或撤销无法收回。建议在三端测试中加入同 incarnation 重连与到达顺序变化，确认端点继续使用传输四元组与业务幂等规则。
